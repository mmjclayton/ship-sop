## Summary

P14 rewrites every `.claude/settings.json` write site in `setup.sh` to emit the nested `{"matcher":"*","hooks":[{"type":"command","command":"..."}]}` shape instead of the flat `{"command":"..."}` shape Claude Code silently discards, adds a legacy-flat migration path, three shared jq selector constants (`HOOK_NESTED_PROBE`, `HOOK_LEGACY_PROBE`, `HOOK_ENTRY_EXAMPLE`), and a post-install assertion that `exit 1`s if the written entry isn't parseable. P15 fixes three installer defects — `pwd -P` instead of logical `pwd` for `SCRIPT_DIR`/`TARGET` (symlinked clone previously defeated self-install detection), an `-ef` guard in `remove_if_unmodified` placed before the `--force` branch, and an awk `skip=1` fix for the `.gitignore` uninstall block (was `skip=2`, eating one real line after the block) — and adds the repo's first CI workflow (shellcheck, `bash -n`, JSON validation, a hook-shape assertion).

Severity: MEDIUM

## Findings

- `scripts/auto-ship-hook.sh:9-17` — The header comment still documents the pre-P14 flat shape (`{ "command": "scripts/auto-ship-hook.sh" }`) as "what setup.sh adds," which is now false — `setup.sh` writes the nested shape everywhere. This is the one file P14 didn't touch that describes the wiring shape, and it directly contradicts the fix: an operator reading this comment to hand-wire a project (or to sanity-check what `setup.sh` should produce) would reintroduce the exact bug P14 exists to close. Fix: update the comment block to the nested shape, matching `HOOK_ENTRY_EXAMPLE` in `setup.sh:51`.

- `README.md:299-307` (mirrored at `setup.sh:295-301`) — The uninstall jq expression's final filter, `select((.hooks? // null) == null or (.hooks | length) > 0)`, drops any `Stop` entry that already has `"hooks": []` even when that entry's `.command`/none of its nested commands is ours. Verified: `{"matcher":"*","hooks":[]}` sitting alongside our own entry in the same array is silently removed by the uninstall pass, with no other command in it referencing ship-sop. Since a `hooks: []` entry never fires anything, this has no observable effect on Claude Code's behavior, but it does discard a pre-existing (if inert) config node that the removal wasn't asked to touch — e.g. a matcher a user had temporarily emptied, meaning to repopulate. Fix: guard the final select on entries that are literally the products of this pass's own inner filter (e.g. tag entries before filtering, or only drop entries where `has("hooks")` was true *and* the pre-filter length was already 0 for **our** command specifically) — or accept this as intentional and document it in the comment above the expression.

- `README.md:299-307` only — the "Manual fallback" jq snippet is unconditional (no `[ -f .claude/settings.json ]` guard, no existence-of-our-hook check), unlike the equivalent logic in `setup.sh`'s `uninstall_mode` (`setup.sh:287-289`), which only runs the destructive rewrite after confirming a matching entry exists. Verified: running the README snippet against a missing `.claude/settings.json` makes `jq` fail (exit 2), the `&&` short-circuits so `mv` never runs and the real file is untouched, but it leaves a stray 0-byte `.claude/settings.json.tmp` behind in the project. Running it against a settings.json with no ship-sop entry produces a no-op edit that still adds an empty `.hooks.Stop: []` (and `.hooks: {}` if absent) where none existed. Neither is destructive, but the asymmetry with the guarded logic in `setup.sh` is real and this snippet is the one path a user takes specifically when `setup.sh` is unavailable. Fix: prefix the snippet with the same existence/match check `setup.sh` uses, or at minimum `[ -f .claude/settings.json ] &&`.
