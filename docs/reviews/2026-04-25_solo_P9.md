## Notes

**block_on choices are defensible.** HIGH for `code-reviewer` and `silent-failure-hunter` is correct given that CRITICAL is already owned by `security-reviewer` (OWASP-class) and `compliance-reviewer` (legal-exposure-class). HIGH quality and silent-failure findings have bounded blast radius by comparison. Advisory `block_on: never` for `pr-test-analyzer` is also correct — test-coverage gaps are legitimate on refactors, doc-only changes, and interim WIP commits; hard-blocking would produce sustained false-positive friction.

**JSON validates and matches schema.** Both `docs/templates/ship-sop.config.json` and `ship-sop.config.json` pass `jq empty`. All added agent objects supply the required `enabled` field, and `block_on` values (`"HIGH"`, `"never"`) are members of the schema enum (`["CRITICAL", "HIGH", "MEDIUM", "never"]`). The schema's `additionalProperties` on the `agents` object means arbitrary new keys are valid. Template and dogfood configs are structurally identical (verified via `diff`).

**README "Common extensions" section is internally consistent.** The c25d04c split produces two clearly labelled sub-blocks: a language-reviewer JSON snippet (pick one, four options shown) and a stack-specific table (`database-reviewer`, `performance-optimizer`). The two blocks do not overlap and align with the decision file's locked rule that language reviewers stay per-project. The decision file lists more locked-out language reviewers (`java-reviewer`, `csharp-reviewer`, `kotlin-reviewer`, `cpp-reviewer`, `flutter-reviewer`) than the README shows — the README's four-option snippet is intentionally representative, not exhaustive, which is fine.

**Gates tables are consistent.** README and `docs/ship-sop.md` both show 7 gates in the same order with matching descriptions and block-on values. No contradictions.
